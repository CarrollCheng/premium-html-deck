Why Skills

为什么产品经理适合用 Skills？

PM 的工作不是单点写作，而是一条跨角色、跨阶段、容易漏细节的链路。

传统方式

依赖个人经验，质量不稳定

  • 想法散落在聊天、脑图和临时文档里
  • PRD 完整度依赖 PM 个人经验
  • 评审时才发现边界、权限、异常不清
  • 上线后才发现关键数据没有埋
  • 汇报材料临时拼凑，表达成本高
使用 Skills 后

把流程沉淀为可复用工作流

  • 模糊想法被结构化成方案
  • 文档有统一标准和检查逻辑
  • 需求漏洞在评审前提前暴露
  • 研发任务更容易估时和排期
  • 方案更容易被业务、研发、管理层理解
核心变化：不是让 AI 替你做产品判断，而是让 AI 帮你把「想清楚 → 写清楚 → 拆清楚 → 看清楚 → 讲清楚」变成稳定流程。

Core Skill 01

方案发散 Brainstorming Skill

01
从模糊想法到完整方案
适合需求还不清楚、只有一个方向或灵感时使用。它会引导你把目标、用户、场景、模块、架构和数据流梳理出来。
PM 提效点：把脑子里的想法快速变成团队能讨论的方案。

解决什么问题

  • 起点模糊，容易直接跳方案
  • 缺少用户场景和边界
  • 没有系统视角和数据流

典型输入

一句模糊想法
业务背景
目标用户或场景

主要产出

完整设计文档
功能模块
架构与数据流
风险与边界

输入材料→调用 Skill→检查结果→沉淀方案

Core Skill 02

PRD 撰写 Write-a-PRD Skill

02
从方案到高质量需求文档
适合进入正式 PRD 阶段。它不是帮你堆一份看起来完整的文档，而是通过追问暴露逻辑漏洞。
PM 提效点：提前发现目标、边界、路径、权限、异常中的漏洞。

解决什么问题

  • 目标、范围、边界不清
  • 用户路径和异常场景容易漏
  • 评审时被多角色反复追问

典型输入

产品方案
用户故事
业务规则
已有 PRD 草稿

主要产出

结构化 PRD
边界说明
异常场景
验收标准

方案输入→追问补洞→整理结构→形成 PRD

Core Skill 03

需求拆解 Writing-Plans Skill

03
从大需求到可执行计划
适合在 PRD 之后、研发评估之前使用。它会把大需求拆到研发能估时、能排期、能执行的颗粒度。
PM 提效点：让需求从能看懂变成能推进。

解决什么问题

  • 需求太大，研发难估时
  • 前后端、测试、设计依赖不显性
  • 阶段计划和优先级不清楚

典型输入

PRD
功能列表
阶段目标
研发约束

主要产出

模块拆解

依赖关系
验收标准

Core Skill 04

数据埋点 Analytics-Tracking Skill

04
从上线功能到数据闭环
适合在上线前设计数据体系。它强调先明确要回答什么业务问题，再设计指标、事件、属性和看板。
PM 提效点：让产品上线后可衡量、可复盘、可继续优化。

解决什么问题

  • 上线后发现关键数据没埋
  • 埋点很多但无法支撑决策
  • 指标、事件、漏斗口径不一致

典型输入

业务目标
用户路径
关键行为
实验假设

主要产出

指标体系
事件设计
属性字段
漏斗与看板

业务问题→指标定义→事件设计→数据闭环

Visual Skill 01

baoyu-diagram

05
把复杂逻辑画清楚
适合把流程、架构、权限、状态、数据流等复杂内容可视化。让评审从“读文字”变成“看关系”。

  • 评审缺少统一图示

角色关系

主要产出

Visual Skill 02

baoyu-infographic

06
把复杂信息做成图文表达
适合汇报、复盘、业务宣讲。把方案价值、功能对比、数据结论转成更容易理解的信息图。
PM 提效点：让方案更像能被快速理解的产品表达。

解决什么问题

  • 方案内容多，听众抓不到重点
  • 汇报材料缺少视觉层次
  • 复杂结论不适合长文呈现

Workflows

把 Skills 串成 PM 工作流

单个 Skill 能提效，真正有价值的是按真实场景组合使用。

从 0 到 1 做新功能

方案发散→baoyu-diagram→PRD 撰写→需求拆解→数据埋点

把产品价值包装成用户能理解、愿意点击的素材。
